# Matched-run analysis and exact financial reconciliation

These Python analysis tools use the standard library. They do not build or modify production code, execute workloads, write to infrastructure, release reservations, or approve a tradeoff.

Run each performance profile separately:

```powershell
python scripts/qualification/summarize.py --directory PATH/measure --configuration PATH/configuration.json --catalog PATH/catalog.json --output PATH/summary.json
```

`--catalog` is an explicit local path override for a catalog recorded with a Linux container path. The catalog hash is retained. Cohort configuration must include its actual compilation `sourceSdk`, exact `sourceSha`, and expected runtime. Case/configuration counts, IDs, architecture, strict client/provider observations, observer window/process/runtime identity, separate warmups, inventory and execution cleanup are checked. A profile prefix is supported. `profileDirectoryScope` identifies the directory; profiles are never pooled for latency statistics.

Output contains independent per-run statistics, their median/range, and medians/ranges of same-run paired ratios. It does not pool request quantiles. Completed responses, cancellation scenarios, unknown failures and declared legacy Responses failures remain separate. A known 502 is never successful throughput. The frozen validator proves complete content/tools/usage/event contracts; this parser cross-checks counters and provider boundaries. It does not replay raw frames or claim to measure network flush completion. Provider/client runtime must be constant; comparisons cannot cross architectures or use unequal deterministic payload ID widths.

Default working diagnostics require five independent pairs; p95 requires100 observations in each run and p99 requires1000 in each run. Per-run small-sample tails remain visible but cannot support the tail diagnostic. The phase0 proposed full-response p50/p95/p99 budget is `after<=max(before*1.05,before+2ms)`; the parser retains raw paired ratios and also computes the median candidate/budget ratio from each same-run bound. Other diagnostics are throughput ratio>=.95, window-normalized CPU/allocation<=1.05, sampled working set peak<=1.10. Every result retains `acceptanceGranted=false`: passing a working threshold does not accept a tradeoff or qualify production. Observer windows include client startup/finalization and server background work; there is no idle subtraction or pure per-request CPU/allocation attribution. These cohorts change application source, compiler and runtime together; their differences are not isolated runtime causation.

New collections use identical `logicalCaseId` request payloads across cohort providers and unique artifact `caseId` filenames. A fresh frozen provider per cohort/run supplies explicit `providerInstanceId`; request markers may repeat across instances but cannot repeat inside one instance. Billing correlation IDs remain unique across the selected cohort's financial profiles. Historical collections without those fields retain the original single-provider uniqueness rule. Equal-length prefixes alone do not imply equal BPE tokenization; the old smoke is preserved as a harness smoke, not a matched payload performance comparison.

First-content and provider-write-begin/client-content p50/p95/p99 are reported separately from full validation. The shared-clock provider proxy is not a socket-flush measurement. Server admission-to-first-provider-chunk and first-awaited-flush histogram deltas must exactly match standard/enhanced/cancellation request counts; missing metrics, count mismatch and resets fail collection validation. Other endpoints require absent/zero deltas and report N/A. These histograms provide means, not raw p99. Their first flush may be a role event before content. First-event comparisons remain descriptive with no invented production threshold. Per-run lifecycle rows separate readiness, known-spend drain and graceful shutdown. Window GC generation counts and post-window forced-GC/latest-GC memory snapshots retain their measurement scopes.

Reconcile the snapshot against **all** measured and warmup profiles that wrote to that independently seeded cohort database:

```powershell
python scripts/qualification/reconcile.py --snapshot PATH/accounting/snapshot.json --directory PATH/phase0-measure --directory PATH/core-measure --expectation PATH/expectation.json --output PATH/financial.json
```

`expectation.example.json` documents the base schema. Add exact `sourceSha` and `profileSources` (the list of included manifest SHA256 values) for a frozen qualification. Set `knownResponsesFailure` from the cohort configuration; both identical f68 smoke controls set it true, even though one is labelled `fixed`. The known failure retains missing logs/known charges and always fails financial qualification. This flag is not a waiver.

The schema is the preserved phase0 `snapshot.json`: PostgreSQL exact string amounts and Redis group scalars/hashes/pending/processing values. JSON duplicate keys and nonfinite numbers are rejected. Financial calculations use Decimal with80-digit precision, exact1e8 spend units, no binary float and no monetary tolerance. The checker verifies fixture pricing and database IDs, token/status/cost cohort multisets, raw log/count/token totals, positive billed rows, original ledger amounts/idempotency/continuity, balance/spend/credits, exact bounded settlements and unresolved hold arithmetic. Marker IDs are scoped by profile/provider instance; repeated billing IDs are rejected. Supplied profile order and initial cumulative log counts must agree, and any initial-count manifest hash must refer to a supplied preceding profile. Group-batch accounting intentionally has no key history rows.

Before-usage cancellation uses persisted estimated prompt/output token cohorts priced with the fixture rates, cross-checked against correlated Redis settlement histograms and reservation bounds. It never assumes free work or bills unseen final10/5 provider tokens. This is an independent cross-store/formula check, not a replay of tokenizer estimation. After-usage cancellation requires provider disconnect/usage evidence and retains known spend plus exact remaining unresolved hold. Open holds prevent `fullyReconciled`; they are not released by this tool. Normal RequestLogs lack universal billing IDs: database validation is an exact multiset, not an invented universal per-request SQL join. Chat/Responses wire correlation maps to the reservation by the explicit source contract; audio has no parent reservation.

The existing snapshot does not enumerate Wolverine queues. `messagingDrainQualified=false` is explicit for the snapshot alone. New profile configurations require separate live-host queue/SQL drain receipts; the analyzer checks cumulative logs, exact final money, all known spend queue counters, fixed probe binary/SDK/runtime/query identity, and successful drain/host exits. `knownPersistedSpendDrainQualified` records that bounded scope, not provider completeness or settlement of unresolved holds. Redis pending zero and host exit0 alone do not prove ledger settlement. PostgreSQL/Redis reads are separate read-only commands rather than a distributed atomic snapshot.

Exit0 for summarization means collection validation, not all workload success or performance acceptance. Exit0 for reconciliation means its exact financial invariants passed; exit2 retains failed checks or an evidence error. Known legacy defects deliberately return2. Run unit tests with:

```powershell
python -m unittest discover -s scripts/qualification -p test_qualification.py -v
```

The 40 tests include corrupt framing/provider boundaries, config/architecture/payload mismatch, scoped logical marker reuse versus duplicate billing IDs, provider process/exit identity, small-sample p99 despite pooled counts, relative/absolute diagnostic-only latency thresholds, strict histogram deltas/resets, forged drain successes, exact one-unit/subunit financial mutations, token formula/bound/hold violations, known failures under a `fixed` label, source identity mismatch, pressure socket controls and adverse fast/paced contrasts.

The separate `Pressure` project preserves the phase0 pressure source/catalog bytes and pins SDK 10.0.404. Its actual receive-buffer values and provider application-write spans are checked, and `pressureContrasts` retains within-runtime paired fast/paced CPU/allocation/memory/duration values without inferring stable p99 or automatically declaring pressure propagation. See `Pressure/PHASE2.md` for the separate execution/financial scope.

The preserved real smoke has24 case-run rows from three runs of two identical f68/.NET10 controls. `smoke-replay-configuration.json` adds SDK10.0.404 from the pinned packaging Dockerfile and an explicit same-control comparison; original execution artifacts remain untouched. It records that its derived configuration hash differs from the original execution configuration. The preserved pre-V2 `smoke-summary.json` validates the collection and retains six known Responses502s; no performance inference is made. Legacy recorded conservation passes with a.000225 missing-known-charge defect. The `fixed` smoke label additionally fails conservation: logs.0084 versus ledger.0059; two durable PostgreSQL spend events total.0025. `smoke-gap-analysis.json` binds that diagnosis to raw dump lines/logs/hashes. Neither smoke cohort financially qualifies.


`ObserverV2` adds only `observerVersion=2`, `isServerGc`, and an ordinal-key-sorted string dictionary from `GC.GetConfigurationVariables()` to each snapshot. Configuration is sampled once at startup using invariant conversion; it is policy metadata, not live DATAS heap history. The original `Observer` source remains unchanged. Both runtime arms use the exact same SDK10.0.404-compiled V2 hook with JSON reflection disabled. This adds metadata serialization overhead to both arms and defines a new observation cohort; it does not retroactively repair frozen phase0 or failed V1 observations.

The official [runtime fix131069](https://github.com/dotnet/runtime/pull/131069) explains why `.NET10.0.15` ServerGC lifetime allocation counters can omit retired DATAS heaps. **Every** such V2 window has `allocationEvidence.valid=false`, including positive deltas. Raw start/end/delta and the nonmonotonic flag remain visible. Allocated-bytes/request is null; allocation ratios and budgets are unavailable, never selectively computed from positive windows. Unknown-runtime, .NET11, workstation, or metadata-free negative allocation deltas still fail. CPU/time/GC-count and all other invariants remain strict. Historical positive windows without GC metadata cannot qualify allocation comparisons either. No approximate counter, clamp, allocation error tolerance or GC policy change is used.

`collectionValidated=true` certifies evidence collection and unaffected invariants only. Top-level `allocationGateSatisfied=false`, `allocationGateStatus=open-unavailable`, and `performanceAcceptanceGranted=false` keep production-default allocation/performance acceptance explicitly open. Even complete diagnostic-only comparisons do not grant acceptance. New tests use actual source-generated V2 server-GC metadata from the fixed binary on both runtimes, reject counter/config corruption, and prove favorable positive counters cannot enter allocation ratios or pass their budget.
